# Deploying Trimly

Target: **Render** (Docker web service + managed Postgres) with **Cloudflare R2**
for shop logos. Roughly **$13/month**: $7 web service + ~$6 database. R2's free
tier (10 GB, no egress fees) covers the logos.

Why R2 instead of a Render disk: a disk pins the service to one instance and
disables zero-downtime deploys, and the container filesystem is wiped on every
deploy anyway. Logos are content-addressed, so they cache forever.

Files that make this work:

| File | Purpose |
|---|---|
| [Dockerfile](Dockerfile) | Python 3.12 image, non-root, binds `0.0.0.0:$PORT` |
| [.dockerignore](.dockerignore) | Keeps `.env`, tests, docs and local DBs out of the image |
| [render.yaml](render.yaml) | Blueprint: service, Postgres, health check, pre-deploy migrations |
| [app/integrations/storage/](app/integrations/storage/provider.py) | `local` (dev) and `s3` (production) logo storage |

The app also rewrites Render's `postgresql://` URL to the psycopg 3 driver in
[config.py](app/core/config.py#L8), so no manual URL editing is needed.

---

## 0. Push the code to GitHub

There is no git repository in this folder yet, and Render deploys from one.

```bash
git init -b main
git add -A
git commit -m "Trimly: booking API, customer + owner portals, assistants"
gh repo create trimly --private --source=. --push    # or create it in the UI and add the remote
```

`.env` is already in `.gitignore`; confirm with `git status --short | grep env`
— you should see nothing. If `.env` was ever committed in another copy of this
project, rotate `JWT_SECRET_KEY` and the payment keys before going live.

## 1. Create the R2 bucket

1. Cloudflare dashboard → **R2** → create a bucket, e.g. `trimly-logos`
   (R2 needs a payment method on file even on the free tier).
2. **Settings → Public access**: either connect a custom domain (recommended,
   e.g. `cdn.yourdomain.com`) or enable the `r2.dev` development URL (fine for a
   demo; rate-limited, not for production traffic).
3. **Manage R2 API Tokens → Create token**, permission *Object Read & Write*,
   scoped to this bucket. Copy the **Access Key ID** and **Secret Access Key** —
   the secret is shown once.

You will end up with:

```
S3_ENDPOINT_URL=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
S3_BUCKET=trimly-logos
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_PUBLIC_BASE_URL=https://cdn.yourdomain.com     # or https://pub-<hash>.r2.dev
```

## 2. Deploy with the Blueprint

1. Render dashboard → **New → Blueprint** → pick the repo. Render reads
   `render.yaml` and shows the service plus the database.
2. It prompts for the values marked `sync: false`. Paste the four R2 values.
   There is no site URL to enter: Render assigns `https://<service>-<hash>.onrender.com`
   when the service is created and injects it as `RENDER_EXTERNAL_URL`, which
   [config.py](app/core/config.py) uses when `PUBLIC_BASE_URL` is unset.
3. **Apply**. The build runs `pip install`, then `alembic upgrade head`, then
   starts uvicorn.
4. When it is live, copy the URL from the service header (or the
   `Your service is live at …` line in the deploy log) for the checks below.
   Only set `PUBLIC_BASE_URL` later, and only if you add a custom domain — a
   custom domain must override the `onrender.com` one for payment and WhatsApp
   links to be correct.

`JWT_SECRET_KEY` is generated by Render, not stored in the repo.

## 3. Verify the deploy

Do these in order; each one fails loudly if something is wrong.

```bash
BASE=https://trimly-xxxx.onrender.com   # from the service header in the dashboard
curl -s $BASE/health                      # {"status":"ok"}
curl -s -o /dev/null -w '%{http_code}\n' $BASE/          # 200 (customer portal)
curl -s -o /dev/null -w '%{http_code}\n' $BASE/dashboard # 200 (owner portal)
curl -s -o /dev/null -w '%{http_code}\n' $BASE/docs      # 200 (OpenAPI)
```

Then in the browser, on the deployed origin:

1. Register an owner, create a shop, add a service.
2. Upload a logo in **Settings**. The `<img>` must load from your R2 domain, not
   from `/uploads`, and the object must appear in the bucket under `shops/`.
3. Register a customer, ask the assistant *"cheapest haircut near me"*, book a
   slot, and confirm the booking appears in the owner dashboard.
4. Ask the owner assistant *"how many bookings today?"* and check the count
   matches the bookings list.

If the logo upload returns 500 with `STORAGE_BACKEND=s3 but ... is not set`, the
bucket env vars did not reach the service. If it returns 403 from the storage
provider, the API token lacks *Object Read & Write* on that bucket.

## 4. Migrations and later deploys

- Every deploy runs `alembic upgrade head` before the new instance takes
  traffic, so a migration failure blocks the deploy instead of half-applying.
- New migration locally: `alembic revision --autogenerate -m "..."`, commit it,
  push. Never edit a migration that has already run in production.
- Rollback: Render → **Rollbacks** restores the previous image. Schema changes
  are not reverted, so keep migrations backwards-compatible for one release.

## 5. Things that differ from your laptop

| Local | Deployed |
|---|---|
| `DATABASE_URL=...@postgres:5432` (compose) | injected by Render, internal URL |
| logos in `./uploads`, served by FastAPI | objects in R2, served by the bucket domain |
| `.env` file | dashboard env vars / Blueprint |
| `docker compose up` | `build` + `preDeployCommand` + `startCommand` |
| Redis container | not used by any code path; no Redis in production |

## 6. Domain and custom URL (optional)

The `onrender.com` URL works immediately and is fine to demo. Buy a domain only
when the URL needs to be permanent, and buy it separately from hosting — Render
runs the app, a registrar sells the name.

| Registrar | Link | Notes |
|---|---|---|
| Porkbun | <https://porkbun.com> | Cheap renewals, free WHOIS privacy, no upsells |
| Cloudflare Registrar | <https://www.cloudflare.com/domains/> | Sells at wholesale cost; requires the domain to use Cloudflare DNS; limited TLD list |
| Namecheap | <https://www.namecheap.com> | Large catalogue, frequent first-year discounts |

A `.com` runs roughly $10-12/year. Then:

1. Render dashboard → your service → **Settings → Custom Domains → Add Domain**.
   Add both `example.com` and `www.example.com`; Render redirects one to the
   other depending on which you add first.
2. At the registrar's DNS panel, point the records at your service's
   `onrender.com` hostname:
   - `www` → **CNAME** → `trimly-xxxx.onrender.com`
   - root domain → **CNAME** if your provider supports flattening (Cloudflare
     does), otherwise **A** → `216.24.57.1`
   - **Delete any `AAAA` records** — Render is IPv4-only and stale v6 records
     break certificate issuance.
3. Wait for Render to show the certificate as issued (usually minutes), then set
   **`PUBLIC_BASE_URL=https://example.com`** in the environment. Without this the
   app keeps generating payment and WhatsApp links against the `onrender.com`
   host, which still resolves and makes the mistake easy to miss.

## 7. Cost and limits

- Web `0.5c-512mb` **$7/mo** — 512 MB RAM is enough for this app; the assistant
  builds its index per request in memory over a small corpus.
- Postgres `0.1c-256mb` **~$6/mo**. Free Postgres expires after 30 days.
- R2 free tier: 10 GB-month, 1M writes, 10M reads, zero egress.
- Single instance, no autoscaling. If you ever need two instances, R2 already
  makes that safe — the only thing tied to one machine would have been uploads.

## 8. Rehearse the image locally (optional)

```bash
docker build -t trimly .
docker run --rm -p 8000:8000 --env-file .env \
  -e DATABASE_URL=postgresql://booking:booking@host.docker.internal:5433/booking \
  trimly
```

The compose Postgres from `docker-compose.yml` listens on host port 5433, so
this exercises the same image Render builds without touching production data.
